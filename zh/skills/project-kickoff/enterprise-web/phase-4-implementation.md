# Phase 4: 代码实现

> **阶段目标**: 按模块分解、逐模块实现、持续验证质量  
> **前置条件**: 已完成系统设计（数据库、API、安全）  
> **核心产出**: 可工作的代码、测试、约定快照  
> **关键原则**: 先跑通再完善、模块间一致性、人机协作对齐

---

## 1. 实现顺序原则

### 1.1 按 Phase 划分模块组

将 PRD 中的功能模块按优先级分组：

| Phase | 目标 | 包含内容 | 依赖关系 |
|-------|------|----------|----------|
| Phase 1 | MVP 跑通 | 核心业务流程（认证 + 核心功能） | 无 |
| Phase 2 | 完整权限 | 权限控制、管理功能 | 依赖 Phase 1 |
| Phase 3 | 体验增强 | 通知、辅助功能 | 依赖 Phase 2 |
| Phase N | ... | ... | ... |

### 1.2 模块依赖原则

- **先基础后业务**：认证、权限等基础模块先于业务模块
- **先后端后前端**：API 先行，前端对接
- **先核心后增强**：P0 功能先于 P1/P2

## 2. 单模块执行流程

每个模块从开始到完成，经过以下阶段：

```
┌──────────────────────────────────────────────────────────────────┐
│                      单模块执行流程                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① 对齐        ② 分解         ③ 生成          ④ 执行            │
│  ┌────────┐   ┌────────┐   ┌────────┐      ┌────────┐          │
│  │ 人机   │ → │ 任务   │ → │ Prompt │ →    │ 代码   │          │
│  │ 理解   │   │ 分解   │   │ 生成   │      │ 实现   │          │
│  │ 对齐   │   │        │   │        │      │        │          │
│  └────────┘   └────────┘   └────────┘      └────────┘          │
│       │                                         │               │
│       │    ⑧ 提取        ⑦ 分流       ⑥ 审查   │  ⑤ 验证      │
│       │   ┌────────┐   ┌────────┐   ┌────────┐ │ ┌────────┐   │
│       │   │ 约定   │ ← │ 人工   │ ← │ 独立   │←┘ │ 烟雾   │   │
│       │   │ 提取   │   │ Triage │   │ Review │   │ 测试   │   │
│       │   └────────┘   └────────┘   └────────┘   └────────┘   │
│       │       │                                       ↑         │
│       │       ▼                                       │         │
│       │   输入到下一模块的 ① ──────────────────────────┘         │
│       │                                                         │
└──────────────────────────────────────────────────────────────────┘
```

### 阶段说明

| # | 阶段 | 目的 | 产出物 |
|---|------|------|--------|
| ① | 人机理解对齐 | 确保人和 AI 对流程和目标的理解一致 | 差异记录（如有） |
| ② | 任务分解 | 将模块拆成可执行的 prompt 序列 | 分解清单 + prompt 文件 |
| ③ | Prompt 生成 | 编写具体的实现指令 | prompt 文件组 |
| ④ | 代码实现 | 执行 prompt，生成代码 | 代码 + 测试 |
| ⑤ | 烟雾测试 | 快速验证核心路径能跑通 | 测试结果 |
| ⑥ | 独立审查 | 独立于编码者的代码审查 | 审查报告 |
| ⑦ | 人工 Triage | 人工判断审查发现的问题修不修 | fix prompt + open-issues |
| ⑧ | 约定提取 | 从已验收代码中提取实现约定 | 约定快照（更新） |

## 3. 阶段详述

### 3.1 ① 人机理解对齐

**触发时机**：每个模块开始前

**为什么需要**：人和 AI 各自对"标准流程应该怎么走"有自己的理解，这些理解可能存在偏差。如果不在动手之前暴露偏差，后续步骤会基于不同假设运行，导致返工。

**具体做法**：

1. 人和 AI 各自独立输出对本模块执行流程的理解：
   - 要经过哪些步骤
   - 每步的输入和输出是什么
   - 本模块有哪些特殊考量（依赖、风险）
2. 比对两方输出，识别差异
3. 对差异达成一致后再进入下一步

**示例**：

```
人："这个模块需要先做后端 API，再做前端页面，最后写测试"
AI："这个模块需要先做数据库迁移，再做后端 API，再做前端，测试和 API 一起写"
差异：数据库迁移是否独立步骤？测试什么时候写？
→ 讨论后达成一致
```

**注意**：这不是形式主义的仪式。当模块简单、流程无歧义时，可以快速过一遍确认即可。价值在复杂模块或流程有变化时体现。

**来源**：Phase 2 结束时人考 AI 对标准流程的理解，AI 遗漏了 decompose 的起点输入。这个真实偏差验证了对齐步骤的价值——不是 AI 不会做，而是 AI 对"从哪里开始"的理解和人不一致。

### 3.2 ② 任务分解

将模块拆成有序的实现步骤。

**输入**：
- 设计文档（API 设计、数据库设计、状态机定义）
- 约定快照（从前序模块提取的实现约定）
- 约定快照中的已知不一致列表（可顺手修复的项）

**质量要求**：
- 每个步骤有明确的验收标准
- 步骤间依赖关系显式声明
- 如发现跨模块依赖，必须显式决策处理策略（声明依赖 / 合并模块 / 最小桩接口），不得静默吞并

**跨模块依赖处理**：

| 策略 | 适用场景 | 要求 |
|------|----------|------|
| 声明依赖 | 被依赖模块复杂，不宜合并 | prompt 中注明"假设 X 已完成" |
| 合并模块 | 被依赖模块简单，可控 | 验收清单必须覆盖被吸收模块 |
| 最小桩接口 | 需要依赖但不想完整实现 | 创建桩/mock |

无论哪种策略，人必须确认。

### 3.3 ③ Prompt 生成

将分解结果转为可执行的 prompt。

**质量要求**：
- 内嵌精确的 API 请求/响应模式（不能仅"参考 api-design.md"）
- 包含约定快照作为"项目约定"部分
- 每个 prompt 以 git commit 步骤结束
- fix prompt 必须先用 grep/find 定位实际文件，不假设文件名

### 3.4 ④ 代码实现

执行 prompt，生成代码。

**原则**：
- 先跑通再完善
- 小步提交，频繁集成
- 遵循项目约定快照中的模式

### 3.5 ⑤ 烟雾测试

代码实现后，快速验证核心路径。

**目的**：不是完整测试，而是确认"能跑、主路径通"。

**方式**：
- 手动调用核心 API
- 检查前端页面能否加载和交互
- 确认数据库写入正确

### 3.6 ⑥ 独立审查

由独立于编码的审查者（人或 agent）对照设计文档检查代码。

**审查维度**：
- API 契约一致性（代码 vs 设计文档）
- 前后端字段对齐
- 状态枚举一致性
- 共享数据结构一致性
- 测试覆盖

**产出**：结构化审查报告（每个 finding 有编号、严重度、文件位置）

### 3.7 ⑦ 人工 Triage

审查报告中的 finding 不是全部都要立即修复。人工判断每个 finding 的处置：

| 处置 | 含义 | 去向 |
|------|------|------|
| fix | 本轮修复 | 生成 fix prompt |
| defer | 推迟到后续模块 | 记入 open-issues |
| wontfix | 不修复 | 记录理由后关闭 |

**原则**：报告与修复必须解耦。不是所有 finding 都值得修，人来判断优先级。

### 3.8 ⑧ 约定提取

从已验收的代码中提取实现约定，更新约定快照。

**提取内容**：
- 结构约定（分层、文件组织）
- 命名约定（函数、变量、路由）
- 模式约定（错误处理、认证注入、分页）
- 共享接口约定（日期格式、ID 格式、响应结构）
- 基础设施约定（Docker、环境变量、端口）

**重要**：仅从已验收的、能工作的代码中提取。有问题的代码中的约定不可靠。

约定快照作为下一个模块 ② 任务分解的输入，形成反馈循环。

## 4. 实现原则

| 原则 | 说明 |
|------|------|
| **先跑通再完善** | 先实现核心流程，再优化细节 |
| **持续集成** | 小步提交，频繁集成 |
| **模块间一致性** | 遵循约定快照中的已有模式 |
| **代码规范** | 遵循语言/框架的最佳实践 |
| **容器化开发** | 开发环境即部署环境 |

## 5. 建议的实现顺序

```
1. 基础设施
   ├── 项目骨架搭建
   ├── 数据库连接
   ├── 配置管理
   └── 日志框架

2. 认证模块
   ├── 用户模型
   ├── 注册/登录
   ├── JWT 签发/验证
   └── 权限中间件

3. 核心业务模块
   ├── 按 P0 优先级实现
   ├── 每个模块走完整执行流程（①-⑧）
   └── 配套单元测试

4. 管理后台
   ├── 用户管理
   ├── 配置管理
   └── 数据概览

5. 前端实现
   ├── 路由与布局
   ├── 认证流程
   ├── 核心页面
   └── 管理后台
```

## 6. 常见问题

### 模块 1 需要走完整流程吗？

模块 1 是约定的来源，没有前序约定可参考。它的流程从 ② 开始（跳过 ① 中的约定快照输入），到 ⑧ 时产出第一份约定快照。

### 如果模块很小怎么办？

流程中的每个步骤可以轻量执行。小模块的 ① 可能就是一句"和上个模块一样的流程"，⑧ 可能只新增两行约定。流程不省略，但深度按需调节。

### 审查发现问题太多怎么办？

这正是 ⑦ Triage 存在的意义。不是所有问题都要当场修。按严重度分流，CRITICAL/HIGH 立即修，MEDIUM 可以 defer，LOW 可以 wontfix。避免陷入修不完的循环。
