# 复盘记录：聚合性文档漂移

> **项目**: MIMIR 方法论仓库  
> **日期**: 2026-02-04  
> **类型**: 流程改进（Dogfooding）  
> **贡献者**: 项目团队

---

## 背景

MIMIR 自己的文档遭遇了它教别人避免的一致性问题。SKILL-INDEX 文件——作为所有 skill 的中央目录——比仓库其他部分落后了 5 个版本（停留在 v1.3，而仓库已到 v1.7）。

### 事件经过

1. v1.3 (2026-01-30): 添加 meta-knowledge/ skill。SKILL-INDEX 已更新。
2. v1.4 (2026-01-31): 添加 claude-code-prompt/ skill。README 已更新。**SKILL-INDEX 未更新。**
3. v1.5–v1.7 (2026-02-01~02): 多次 skill 更新，添加 UI/UX 原则。每次都更新了 README。**SKILL-INDEX 仍在 v1.3。**
4. v1.8 (2026-02-04): 添加 review-agent/ skill。发现 SKILL-INDEX 结构树完全缺失 3 个 skill 目录。

讽刺的是：MIMIR 里包含 `doc-dependencies-template.md` 和 `change-review-checklist-template.md`，专门用来防止这种问题。但它们没有被应用到 MIMIR 自己的文件上。

---

## 根因分析

真正的模式不是特指"索引文件"。而是**聚合性文档**——汇总多处来源信息的文件。

### 聚合性文档为什么容易漂移

| 特征 | 为什么导致漂移 |
|------|----------------|
| **不是"主角"** | 添加 skill 时，SKILL.md 是主要交付物。索引只是附带效果。 |
| **无归属信号** | 修改 `claude-code-prompt/SKILL.md` 不会让人联想到"也要更新 SKILL-INDEX"。依赖关系不可见。 |
| **仍然"看起来没问题"** | 过时的索引不会立即出错。读起来没问题。过时是沉默的。 |
| **人人都该更新，但没人负责** | 每次添加 skill 都应该更新它，但没有哪个 skill "拥有"它。 |

### 一般项目中的等价物

这不是方法论仓库特有的。同样的模式出现在：

- **API 文档汇总页** — 单个接口文档保持最新，但列出所有接口的汇总页落后
- **CHANGELOG / 发布说明** — 功能上线了，changelog "以后再更新"（即永远不更新）
- **README 功能列表** — 代码添加了新功能，README 还在描述 v1.0
- **配置参考文档** — 新增配置项，参考文档未更新
- **架构决策记录 (ADR) 索引** — 单个 ADR 写了，索引没更新
- **新人引导文档** — 系统变了，引导文档还在描述旧架构

**共同特征**：这些文件聚合的信息，其真实来源在别处。它们永远是派生的，不是主源。

---

## 我们学到了什么

### 1. 聚合性文档需要显式触发器

之前的复盘（`retro-doc-consistency.md`）正确识别了文档之间存在隐藏依赖。但它关注的是**对等依赖**（UI 原型 → API 设计）。这次发现了不同的依赖类型：**子 → 父聚合依赖**。

```
对等依赖:     API 设计 ←→ 状态机         （两者都是主源）
聚合依赖:     SKILL.md → SKILL-INDEX      （子项汇入父级汇总）
```

聚合依赖更难捕获，因为子文件自身是完整且正确的。父级的过时从子级视角是不可见的。

### 2. 更新中的"距离偏差"

做改动时，人（和 AI agent）自然会更新"离改动最近"的文件：

```
离改动的距离:
  近:   SKILL.md（刚创建的文件）            ← 总是更新
  中:   README.md（提到这个 skill 类别）     ← 通常更新
  远:   SKILL-INDEX.md（列出所有 skill）     ← 经常遗忘
```

文件离改动点越远，越容易被遗忘。这是认知偏差，不是流程失误——所以流程必须补偿它。

### 3. 沉默的过时比大声的报错更危险

过时的 SKILL-INDEX 不会抛错。它仍然能渲染、读起来没问题、仍然"能用"。唯一的症状是新 skill 对通过索引导航的人不可见。这种沉默的失败模式特别危险——你不知道它错了，直到有人真的尝试用它作为入口。

---

## 解决方案：聚合性文档检查清单

### 加入变更审查流程

当项目中**新增任何文件或目录**时：

```
□ 识别所有引用该文件父级范围的聚合性文档
□ 更新每个聚合性文档的：
    □ 目录/结构树
    □ 汇总表格
    □ 版本历史
□ 如果聚合性文档有自己的版本号，则递增
```

### MIMIR 具体规则

对 MIMIR 而言，任何添加/删除/重命名 skill 目录的改动必须更新：

1. `SKILL-INDEX.md`（双语）— 结构树 + 可用 skill 表 + 版本历史
2. `MIMIR-README.md`（双语）— 目录树 + 项目类型表 + 版本历史
3. `README.md`（根目录）— 结构概览 + 支持类型 + 版本历史

### 一般项目应用

对于任何项目，在启动时识别你的聚合性文档：

| 聚合性文档 | 触发条件 |
|------------|----------|
| API 参考索引 | 任何新增/删除的接口 |
| CHANGELOG | 任何面向用户的变更 |
| README 功能列表 | 任何新功能 |
| 配置参考 | 任何新配置项 |
| 架构概览 | 任何新服务/组件 |

将这些作为提交/审查流程中的显式检查项。

---

## 核心收获

1. **聚合性文档沉默地漂移** — 它们是派生的而非主源，所以过时不会显性地破坏任何东西
2. **距离偏差** — 文件离改动点越远，越容易被遗忘
3. **流程必须补偿认知偏差** — 依靠显式检查清单，而非人类记忆
4. **吃自己的狗粮** — 如果你的方法论教一致性，就把它应用到方法论自身
