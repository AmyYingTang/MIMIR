## 背景

质量原则 #10、#11、#12 分别在 s-1-1 和 s-1-2 中被首次发现并提炼。s-2-2（权限管理模块前端 + 集成）的开发和验证过程中，这三条原则再次被独立验证——相同的失败模式在不同模块、不同开发者上下文中重复出现。

这不是"回顾已知问题"，而是**同一条原则在新场景中的自然涌现**——证明这些原则不是个别事件，而是 Agent 行为的稳定模式。

## 实证 1：#11 FullStackFix — 修复只改一层

### 原始原则（s-1-2 提炼）

> 修复 Prompt 必须列出每一个受影响层的改动。Agent 倾向于只修一层就停。

### s-2-2 中的重现

**场景**：s-2-2 的 fix prompt 修复后端权限校验集成逻辑，但没有同步创建前端权限分配页面。

**后果**：后端权限 API 已就绪，但前端没有对应的调用界面。不得不追加 `fix-s-2-2-permission-integration.md` 来覆盖全栈。

**与原始实例的对比**：

| | s-1-2 实例 | s-2-2 实例 |
|---|---|---|
| **触发点** | 后端新增 `/chips/available`，前端仍调旧端点 | 后端权限校验集成完成，前端缺权限分配页 |
| **遗漏层** | 前端调用 + 测试用例 + 旧端点清理 | 前端页面 + 前端 API 调用 |
| **根因** | fix prompt 只描述了后端改动 | fix prompt 只描述了后端集成 |

**结论**：模式完全一致。Agent 的"只修报错层"倾向不是偶发的，是结构性的。

## 实证 2：#12 InlineAPIContract — 响应结构偏离

### 原始原则（s-1-2 提炼）

> Prompt 必须内嵌精确的 API 请求/响应 JSON 模式。Agent 在生成大量代码时会偏离引用文档。

### s-2-2 中的重现

**场景**：`PermissionAssignment.vue` 中前端写了 `res.data.permissions` 来解包权限列表，但后端实际直接返回数组（不包裹在 `.permissions` 字段中）。

**根因**：Prompt 写了"参考 api-design.md"但没有内嵌精确的响应 schema。Agent 按自己的猜测加了一层 `.permissions` 解包。

**与原始实例的对比**：

| | s-1-2 实例 | s-2-2 实例 |
|---|---|---|
| **API** | `GET /chips/available` | `GET /permissions` |
| **偏离方式** | 字段名不同 (`id` vs `chip_id`) | 嵌套层级不同 (`.permissions` vs 直接数组) |
| **根因** | Prompt 未内嵌 schema | Prompt 未内嵌 schema |

**结论**：Agent 的偏离方式不同（字段名 vs 嵌套层级），但根因完全相同。

## 实证 3：#10 DiscrepancyReport — 跨模块约定自然闭环

### 原始原则（s-1-2 提炼）

> 发现参考文档间不一致时，Agent 自行解决但必须报告差异并修补源文档。

### s-2-1/s-2-2 中的验证

**场景**：s-1-2 review 发现 `FUNCTION_TYPE_NAMES` 在三处重复定义（seed.py、API router、前端常量），值不完全一致。这被记入 conventions inconsistency 列表。

**闭环路径**：s-2-1 任务分解时扫描 inconsistency 列表，发现 P01 恰好要创建 `constants.py`（权限模块的常量定义）。Agent 在 P01 执行时建立了权威定义并清理了三处重复——零额外成本，没有专门的"修复冲刺"。

**模式验证**：convention 文档作为"跨模块修复队列"的模式在 s-2-1 中首次被验证。不一致问题的发现和修复分属不同模块、不同时间，但通过 convention snapshot 实现了自然桥接。

## 对 MIMIR 的意义

### 1. 原则的"硬化"

一条原则首次出现时可能只是"一个教训"。当同样的模式在不同模块、不同上下文中重复出现，原则从"经验"硬化为"规律"。

当前硬化状态：

| 原则 | 首次发现 | 二次验证 | 状态 |
|------|----------|----------|------|
| #10 DiscrepancyReport | s-1-2 | s-2-1 自然闭环 | ⬛ 硬化 |
| #11 FullStackFix | s-1-2 | s-2-2 权限集成 | ⬛ 硬化 |
| #12 InlineAPIContract | s-1-2 | s-2-2 权限分配页 | ⬛ 硬化 |

### 2. 螺旋继续

这是 `retro-methodology-spiral.md` 中记录的演进链路的自然延伸：

```
s-1-1 → 质量原则 #1–#9 诞生
  ↓
s-1-2 → #10–#12 诞生 + DependencyResolutionGate
  ↓
s-2-1 → Gate 强化 + convention-as-fix-queue 验证 + #10 闭环
  ↓
s-2-2 → #11、#12 二次验证 + #14 ErrorCodeFidelity 诞生  ← 本复盘
```

每个模块既消费前序模块积累的知识，又产生新的知识给后续模块。螺旋持续上行。
