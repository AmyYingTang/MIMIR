# Skill: Review Agent — 独立代码审查

> **版本**: v0.1  
> **创建日期**: 2026-02-04  
> **最后更新**: 2026-02-04  
> **分类**: 质量保障  
> **运行时**: MIMIR-BO `review-agent/`

---

## 用途

当一个模块被 runprompt-agent（或任何代码生成 agent）构建完成后，由一个**独立的** review 步骤对照设计文档检查实际代码，捕获构建 agent 的自测无法发现的偏差。

**核心洞察**：写代码的 agent 和写测试的 agent 共享相同的上下文和偏差。它们互相对齐，但可能同时偏离设计文档。一个拥有全新上下文的独立审查者，以设计文档为唯一真相来源，能捕获自测遗漏的问题。

---

## 使用时机

```
runprompt-agent 执行 prompt → [代码生成] → ★ review-agent ★ → 人工验收
```

在**每个模块完成后**、人工验收前触发。

---

## 审查维度

| # | 维度 | 捕获什么问题 | 来源 |
|---|------|-------------|------|
| 1 | **API 契约对齐** | 设计文档/后端/前端之间的字段名、路径、响应结构不匹配 | s-1-2: `available_functions` vs `functions` |
| 2 | **共享数据一致性** | 凭据、端口、数据库名在配置文件、seed、测试之间不一致 | s-1-2: `Test@2025` vs `Trainer@2025` |
| 3 | **前后端字段对齐** | 前端调用的 URL/字段与后端实际提供的不匹配 | s-1-2: 前端调 `/tasks/my-chips`，后端是 `/chips/available` |
| 4 | **状态枚举一致性** | DDL ENUM 值 ≠ 状态机文档 ≠ 后端常量 | s-1-2: 4 vs 5 个状态值 |
| 5 | **测试覆盖合理性** | 测试存在但断言错误的字段名；fixture 使用错误的凭据 | s-1-2: 26/26 通过但前端不可用 |

这些维度可扩展。在实践中发现新的失败模式时添加新维度。

---

## 设计原则

1. **独立性** — 审查者不得与构建 agent 共享上下文。它从空白开始，只读设计文档和代码。

2. **设计文档为真** — 当设计与代码不一致时，设计文档是权威。审查报告标记代码不合规，而非设计文档。

3. **只读** — 审查者不修改任何代码。唯一输出是 review report 文件。

4. **穷举** — 每个端点、每个共享值、每个枚举都必须检查。"看起来没问题"不可接受；每项必须明确 PASS/FAIL。

5. **精确** — 每个发现都包含文件路径、行号、期望值和实际值。

---

## 报告格式

输出：项目根目录下的 `review-report-<module>.md`

```
汇总：  ✅ N 通过  |  ⚠️ N 警告  |  ❌ N 失败

每项发现：
- 状态图标（✅/⚠️/❌）
- 检查维度（#1-5）
- 描述
- 文件:行号
- 期望值 vs 实际值
- 修复建议（仅 ❌ 项）

底部：按优先级排序的行动清单
```

## 运行时实现

运行时实现位于 **MIMIR-BO**（`review-agent/` 目录）：
- `review-prompt.md` — 发送给 Claude Code 的 prompt 模板
- `review.sh` — Runner 脚本，填充模板变量并调用 Claude Code CLI

**一致性规则**：本 SKILL.md 中审查维度或设计原则的变更必须同步到 BO 的 prompt 模板，反之亦然。
